# Assessment evidence and outputs (methodology 4.0.0)

The tenant-wide readiness baseline and existing required control IDs remain in place. Configuration establishes the configuration component. Authentication, endpoint protection, DLP and audit require suitable operational records or a current tenant-wide review documenting tested behavior and scope. Missing proof remains unresolved; a confirmed failure produces remediation. Advanced compliance capabilities apply to stated business, legal and regulatory requirements.

The catalog in [assessment_catalog.py](../Core/assessment_catalog.py) covers every check across nine domains: scope and prerequisites; identity; devices; Defender operations; content access; classification and DLP; governance and investigation; applications and consent; external and shadow AI. Every build shows each check, collected and missing evidence, source failures, dates, limitations, applicability and effect on conclusions.

## Standard collection and Restricted behavior

`--preview-collectors auto` is the default. Standard attempts Entra recommendations, Cloud Discovery and Copilot audit when their parent services run. Standard setup requests `DirectoryRecommendations.Read.All`, `CloudApp-Discovery.Read.All` and `AuditLogsQuery.Read.All`. Re-run setup when updating an existing assessment application. `none` disables the automatic supplemental sources. Existing explicit choices remain available; `entra-recommendations` selects that source alone. Restricted excludes these sources and their added permissions.

Entra recommendations and Cloud Discovery use beta APIs. Their advice and candidate service classifications cannot independently pass a foundation control. Discovery retains streams, returned application records and available user/device/IP detail, with explicit network coverage and unmanaged-device limitations. A missing stream or empty candidate set does not establish absent AI use.

Copilot audit uses the supported saved-query API. It may create a query, polls within the existing time budget and follows bounded record pagination. Query ID, status, filter, actual window, page count, partial failures and safe event/resource metadata are retained. Empty or timed-out searches leave operation unknown. Prompt/response content is excluded.

Directory devices, Intune policy assignments and failing settings, Windows protection status, application owners and application permissions, and Defender antivirus health reuse existing read permissions. Child failures retain completed reads. Current documentation checks, their dates and verified scope are exported in **Documentation Verification**. Other product, feature and licensing claims are explicitly unverified. A documentation check does not establish the tenant's entitlement.

The implementation review on October 2, 2026 also checked Microsoft's [Copilot requirements](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-copilot-requirements) and [license options](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-licensing). Plan identity recognition remains an eligibility estimate; confirm the user's actual entitlement and prerequisites for the planned experience.

## Review context and thresholds

Use `assessment_context` in the assessment profile for planned services, ownership, business/legal/privacy requirements, optional pilot context, retirement decisions, exceptions, remediation dates and reassessment plans. `device_activity_days` defaults to 30 and `endpoint_reporting_days` to seven; both accept integers from one to 365. Each exception requires `id`, `owner`, `reason`, `approved_by`, `approved_at` and `expires_at`; a device exception also supplies its stable `device_id`.

`readiness_review.tenant_scope` defines the tenant-wide review boundary. Each `check_reviews` entry requires a catalog `check_id`, matching `scope_id`, `reviewed_at`, `reviewer_role`, `rationale`, `evidence_reference`, `evidence_level` and `result`. Results are `pass`, `fail`, or `not_applicable` for requirements-dependent advanced checks. Evidence levels are `configuration`, `policy_enforcement`, `observed_operation`, and `owner_review`. Operational confirmation requires `observed_operation`, nonempty `tested_behavior` and `tested_scope`, and referenced evidence documenting expected and actual behavior, the population and exclusions. Older reviews without these new fields remain usable as reviews but cannot supply operational confirmation. Configuration-only reviews cannot supply it. Supported legacy `control_reviews` can also provide dated tenant-wide confirmation using the same evidence-level field.

Review freshness remains 35 days. Future, stale and conflicting records stay visible. Pilot scope is optional context for foundation readiness. See [the example profile](../examples/readiness-review.example.json), which deliberately includes unresolved and failed reviews, and [review instructions](READINESS_REVIEWS.md).

Sign-in and audit requests default to seven days. Thresholds and actual source windows are saved in the shared assessment result and workbook. Device identities are reconciled using stable directory IDs, never names alone. Duplicate, conflicting, stale, unmatched and excluded rows remain investigable. Onboarding and current reporting are separate. Percentages require a justified nonzero denominator and record numerator, denominator, population, scope and window. Unknown or zero denominators produce no percentage.

Sharing links, permissions, locations and items remain separate units. Overlapping sharing totals are never presented as unique exposed files. Unique items require retained identifiers; summary exports cannot recreate file, permission or link rows. Label definitions and publication do not establish actual labeling or protection coverage, and DLP simulation does not establish enforcement.

## Deliverables and replay

All deliverables use one shared assessment result:

- HTML opens with the executive recommendation, scope, dates and supported observations. Supplied PDFs add visible **PDF report highlights** near the top, with quoted excerpts, source-page links and follow-up. A visual control baseline and nine area tiles summarize the findings. Action cards, area details and the full collection catalog expand on demand. Configuration observations are distinct from established operational safeguards. Native collected records are summarized as aggregates; supplied PDF excerpts and captures retain their original content.
- Every Excel export produces an assessment workbook under the existing report filename and a sibling **`Technical Evidence - <company>.xlsx`**. The assessment workbook keeps **Start Here**, **Action Plan**, **Findings**, **Coverage**, **Configuration**, **Devices**, **Users & Identity**, **Apps & Consent**, and **Sites & Sharing** visible, in that order. Empty evidence sheets are omitted. **Other Evidence** appears only for incidents, adoption metrics or custom records that have no truthful projection onto the five entity/setting layouts.

  When PDFs are supplied, **PDF Highlights** appears after **Coverage** in the assessment workbook and after **Findings Lineage** in the technical workbook. Its cross-topic excerpts have no assessed finding ID or affected-record population, so they cannot truthfully use the five per-finding evidence layouts. Each row retains a source excerpt, capture and refresh dates, page, hash, follow-up and qualification. Source links open the exact **PDF Extracted Text** page row in the technical workbook, or **Portal Review** metadata for manually supplied notes.
- Optional linked technical evidence pages (`--extra-exports evidence-pages`) list each finding's supporting records, source dates, limitations and verified technical fix in `Evidence/`. Default HTML links directly to workbook evidence and retains the same counts and technical guidance.
- The technical workbook has **Start Here**, **Findings Lineage**, every retained `Raw` and `Evidence` sheet, full selected records consolidated by source dataset, **Technical Recommendations**, source windows, documentation verification, import receipts, device reconciliation/coverage, usage reports, and historical **Prior** sheets. All technical sheets and columns remain visible. The technical `Evidence` lineage rows retain the same detail IDs as HTML evidence pages.
- `--snapshot-json PATH` writes the existing shared assessment result directly as one JSON file. Native records remain in the technical evidence workbook and portable collection package. See [Supported outputs](OUTPUTS.md).
- Raw source and selected investigation rows preserve identifiers, timestamps, nested attributes and provenance. Long fields use continuation columns. Oversized evidence worksheets split into parts, with every supporting range remapped and audited.

Open **Start Here** in the assessment workbook, then **Action Plan** for priorities or **Findings** for all findings. Each finding links to its contiguous evidence block; each row's **Evidence ID** links to an exact visible source row in the technical workbook. Shared records repeat under each finding they support. Device setting states count as settings, not devices; site summary measures do not identify distinct files or people. Wide sharing responses are projected into relevant setting rows, with translated current and recommended values and their original source IDs. Windows protection rows join to retained managed-device inventory. Unknown values stay unknown.

The original **Recommendations**, **Evidence Index**, **Control Results**, **Collection Coverage**, **Run Manifest**, and **Integrity Checks** stay hidden in the assessment workbook with unchanged register columns. Optional **Findings Register**, **App Access Detail**, **Admin Role Detail**, and **AI Adoption Usage** compatibility copies also remain hidden because existing audit consumers read them. Their links open visible technical destinations. Prior-report and baseline importers continue reading the assessment workbook. **Start Here** lists the companion filename and all sheet row counts.

The shared `InvestigationRange(s)`, `RawEvidenceRanges` and `EvidenceRecordsRange(s)` fields retain their existing meanings. New `AssessmentEvidenceRange(s)` and `TechnicalEvidenceRanges` fields describe the two workbook layouts. Source-row reconciliation, per-finding projection counts, unmatched records, range destinations and table names are validated; failures are written to **Integrity Checks** and stop the build. Original retained values, nested data and continuation columns remain available in the technical workbook. No existing XLSX file is post-processed, and CSV-only exports retain their previous behavior.

User usage and prerequisite rows are included in Excel by default. `--include-user-usage-detail` remains a compatibility alias. Protect the assessment package and workbook as confidential evidence.

Evidence schema is **1.1.0**. Explicit reviewed migration routes support methodology **2.0.0**, **2.1.0** and **3.0.0** collections to **4.0.0**, preserving original source files, dates and hashes. Newly required missing detail remains unknown. Historical summaries cannot recreate raw records. Offline rebuilds perform no network collection or documentation lookups; the evaluation date determines freshness consistently for equivalent saved evidence.

Validation includes mocked paging, throttling, permission and licensing failures, partial reads, audit timeouts and Restricted exclusions; configuration/operation distinctions; device reconciliation; privacy; count and link reconciliation; worksheet continuation/splitting; and synthetic offline HTML/workbook audits.
